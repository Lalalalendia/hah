# RAR Rescue v0.8 — проверка вложенных путей перед полной выгрузкой

**Статус:** Draft, реальная приёмка v0.8 ещё не проведена.
Расширение разработано для публичного `Диск 2.rar` на Яндекс Диске:
https://disk.yandex.ru/d/_RSlWomRWmty1w

## Подтверждено на настоящем архиве

- Исходный RAR целиком (244 374 677 байт) возвращает HTTP 500 при прямых попытках скачивания.
- Веб-просмотрщик содержит **1286 объектов = 1199 файлов + 87 каталогов**;
  манифест имеет 88 записей каталогов, включая корень, без ошибок обхода.
- **RAR Rescue v0.7 действительно скачал `LOG4J.XML` автоматически: 1760 байт.**
  По пользовательскому журналу один синтетический клик с
  `userActivationAtClick: false` привёл к браузерной загрузке и статусу
  `downloaded` за десять секунд, без дублирования.
- Загружен только этот один файл, плюс ранее пользователь вручную скачивал
  `README.TXT` вне структуры восстановления. **Скачивание всех 1199 файлов
  пока не подтверждено**. Браузерное завершение само по себе не подтверждает
  CRC/SHA содержимого отдельного файла.

## Почему нужен промежуточный тест v0.8

Первый автоматический файл находился в корне. Это ещё не подтверждает, что
файлы с одинаковыми именами внутри `HELP/...`, `PLUGINS/...` и других папок
не перепутаются и не перезапишутся. Поэтому массовый режим в v0.8
**закрыт**, пока два файла из **разных вложенных каталогов** не будут
запрошены и сохранены по точным относительным путям.

## Установка

1. Сохрани `Disk-2.rar-recovery-report.json` из предыдущей версии, если он
   ещё не сохранён. Локальное хранилище удалённого расширения может исчезнуть.
2. В последнем успешном GitHub Actions workflow **RAR Rescue Extension Checks**
   скачай артефакт **rar-rescue-v08**, распакуй один раз.
3. В `browser://extensions` отключи/удали старые экземпляры, затем
   «Загрузить распакованное расширение» из папки с `manifest.json`.
4. Обнови страницу Яндекс Диска и открой **корень** `Диск 2.rar`.
5. Открой панель расширения; убедись, что указан `RAR Rescue v0.8`.
   Если карта архива не сохранилась, используй **Импортировать карту JSON**:
   полный повторный обход не нужен.

## Порядок проверки

1. **1. Найти файлы** — убедиться, что корень содержит восемь файлов и
   семь каталогов.
2. **Проверить автоматический клик** — при необходимости заново подтвердить
   скачивание одного **ещё не загруженного** небольшого файла, например
   `INDEX.HTM`. Ранее скачанный `LOG4J.XML` повторно запрашивать нельзя.
3. **5. Проверить 2 вложенных файла** — расширение автоматически подберёт
   два текстовых файла из разных вложенных каталогов. Если встречаются
   одинаковые имена в разных папках, предпочтёт такую пару. Выбранные
   полные относительные пути заранее появятся в панели.
4. Расширение самостоятельно пройдёт дерево, на соответствующих папках
   отправит **ровно по одному запросу**, дождётся браузерного завершения
   и проверит, что путь равен
   `Downloads/YandexRARRecovery/Disk-2.rar/<папка>/<имя файла>`.
   Затем вернётся в корень. На этом этапе общее число новых запросов
   ограничено **двумя**.
5. Если обе загрузки подтверждены, панель покажет два исходных пути и
   разблокирует **6. Скачать всё со структурой**. При ошибке, неизвестном
   результате или несовпадении дерева запуск 1199 файлов останется закрытым.
6. Сохрани **Отчёт JSON**: он содержит список всех элементов и статусы файлов.
   Для пустых каталогов есть отдельное действие с явным выбором целевой папки.

Если в двух разных папках нет подходящих незагруженных небольших текстовых
файлов, расширение не должно угадывать и автоматически брать произвольный
огромный бинарный файл. Нужен выбор другой тестовой пары.

## Гарантии и ограничения

- **Строго один запрос на файл.** Тайм-аут не означает неудачную передачу:
  ожидаем до восьми минут регистрации и до 30 минут завершения, при
  неопределённом исходе получаем `needs-review`, останавливаемся.
- Приоритет — сохранение **исходной иерархии** и корректной идентичности пути;
  неверное имя или другая папка не считаются успехом.
- Для файлов с одинаковыми именами в разных каталогах записи манифеста,
  журнала и проверка назначения используют **полный относительный путь**.
- Существующие завершённые загрузки в целевой папке не скачиваются повторно;
  имена не перезаписываются автоматически (`conflictAction: uniquify`).
- Для длинных виртуализированных списков элемент ищется через прокрутку
  **в пределах проверенного каталога**, а не случайным нажатием.
- Вложенный тест требует завершённой карты из 1286 объектов и ранее
  успешной автоматической загрузки одного файла в рамках сеанса.
- Исполняемые файлы (EXE, CMD, SH и другие) никогда не запускаются; в
  двухфайловый пилот выбираются только текстовые расширения.
- В GitHub не отправляются приватные данные сессии, файлы архива, cookies,
  подписанные URL либо пользовательский манифест.

## Регрессионные проверки

- `extension/tests/recovery-plan.cjs` — выбор ровно двух текстовых файлов
  с различными родительскими каталогами, приоритет одинаковых имён,
  отказ от повторов и потенциально исполняемых файлов.
- `tools/test_recursive_fixture.py` — реальный Chrome и модельное дерево
  с двумя `README.TXT` в разных вложенных каталогах; проверяется
  правильное действие в каждой папке и возврат в корень.
- Остальные тесты проверяют безопасные Windows-пути, загрузки с задержкой,
  запрет повторных запросов и импорт 1286-объектного манифеста.

Ожидаемый критерий перехода к массовой загрузке: **один корневой файл плюс два
вложенных файла из разных папок, каждый в точном месте назначения, без дублей**.
